# Changelog

All notable changes to this project will be documented in this file.

## [Unreleased]

### Added
- `chain wait <tx_hash>` waits for the receipt of a sent transaction, for example after a write reported "Not confirmed yet". `--event NAME` (an event of the contract) and `--count N` also require the contract's events, `--timeout SECONDS` sets the wait (default 120), and `--json` prints `tx_hash`, `block_number`, `gas_used`, `status`, `explorer_url`, `event` and `emitted_count`. It sends nothing, needs no wallet key and uses the fallback RPCs. It exits 0 when the transaction is confirmed, 1 when it reverted, was not recorded, was replaced or is not found (`not_found`), and 3 when it is still pending or no RPC can be reached (`connection_failed`). With `--json`, every error after the chain client is built is a JSON object on stdout; errors while it is built (for example an unsupported `CHAIN_NAME` or an invalid `CHAIN_CONTRACT`) are still printed as text. The library method is `ChainClient.wait_for_transaction(tx_hash, expected_event=None, expected_count=1, timeout=120)`, which returns a `TransactionWaitResult` (#167)
- `chain verify --require-active` exits 1 when the record's status is RESTRICTED or DELETED. `chain verify --owner <address>` exits 1 when another address owns the record; the comparison ignores case and checksum, and a value that is not a `0x` address with 40 hex digits is a usage error (exit 2). When a check fails, the command prints `Not verified: <hash> is anchored on-chain, but:` and the failed checks. `chain verify` now always prints the record's `Status:` and `Owner:`. Without the new options, the exit codes are unchanged: a RESTRICTED or DELETED record still exits 0. Its first line no longer says `Verified:`; it reads `Anchored on-chain (status: DELETED): <hash>. The record is not ACTIVE; use --require-active to exit 1 in this case.` `Verified:` is printed only for an ACTIVE record that passes every requested check. `ChainClient.verify()` is unchanged and still checks registration only (#142)
- x402 accepts CAIP-2 chain ids as network names alongside the x402 v1 names: `eip155:84532` is `base-sepolia` and `eip155:8453` is `base`. This works for `X402_NETWORK`, `--x402-network`, `X402Client(network=...)` and the network of a payment option in a 402 answer. The signed payload repeats the option's own network name. The production gateway sends v1 names; x402 v2 headers and payloads are not supported (#143)
- `ChainProvenanceRecord.parents`: the hashes a record was derived from, filled by `get_provenance_chain()` on every node it expands. Nodes at the depth limit, and records from `get()`, have `parents` set to `None`. `chain get --follow --json` shows `parents` on every record, and `chain get --json` shows `"parents": null` (#170)

### Fixed
- A receipt timeout is no longer reported as "Transaction failed". When no receipt arrives within 120 seconds, the write raises `ReceiptTimeoutError` (a new subclass of `TransactionOutcomeUnknownError`, with `tx_hash`, `explorer_url`, `event_name`, `expected_count` and `timeout`). The CLI prints "Not confirmed yet", the transaction hash, the explorer link and the `chain wait` command that resumes the wait (for example `swarm-prov-upload chain wait 0x... --event DataRegistered`), and says not to run the command again. With `--json`, it prints `{"error": "receipt_timeout", ...}` on stdout, with the resume command in `wait_command`. A timeout after the wait moved to a fallback RPC stays "Outcome unknown" (#167)
- A transaction that another transaction with the same nonce replaced is reported as replaced. After a receipt timeout, the client compares the account's mined nonce (`eth_getTransactionCount(address, "latest")`) with the transaction's nonce. If it is above and the transaction still has no receipt, the write raises `TransactionReplacedError` (a new subclass of `TransactionUnconfirmedError`, with `nonce`). The CLI prints "Replaced" and says to check the record with `chain get` before running the command again (for `chain delegate`, the delegate state or the transaction in the explorer); with `--json`, the error is `"replaced"`, and the command exits 1. If the receipt is found then, the write completes as usual. If the nonce check fails, the error stays `ReceiptTimeoutError` (#167)
- **Behaviour change:** a chain command whose transaction may still be mined now exits 3 instead of 1. This applies to a receipt timeout and to every "Outcome unknown" error (`TransactionOutcomeUnknownError`), also when the wait moved to a fallback RPC, and to the failed step of `chain protect` and `chain transform --restrict-original`. Other errors, including "Replaced", still exit 1. When the hash is known, the "Outcome unknown" output also prints the `chain wait` command that resumes the wait, and its JSON has it in `wait_command`. The exit codes are listed in docs/chain-workflows.md (#167)
- The fallback RPCs (the preset ones, or `CHAIN_RPC_URLS`) are now used by every chain command. Only `ChainProvider.health_check()` and `get_block_number()` used them, and no command calls either, so one RPC outage or rate limit failed every chain command. When the RPC in use cannot be reached, times out, or answers with something that is not JSON-RPC, reads (`ChainClient.get()`, `verify()`, `get_by_storage_ref()`, `get_provenance_chain()`, `balance()`) run again on the next fallback. Writes do the same only for the steps before the transaction is sent: the chain ID and contract code checks, building the transaction (gas estimate), the nonce, the gas price and the balance check. `send_raw_transaction` is never repeated: a connection failure there is still reported as `TransactionOutcomeUnknownError`, so a fallback never sends a write twice. Waiting for the receipt can move to a fallback for the same transaction hash; if that RPC then does not return the receipt in time, the write raises `TransactionOutcomeUnknownError` with the hash, not `ChainTransactionError`, because the transaction may still be mined. A read that calls another read (`verify()`, `get_by_storage_ref()` and `get_provenance_chain()` call `get()`) tries each RPC at most once. A fallback must report the chain ID in use before it is used. A JSON-RPC error answer, a contract revert, a receipt timeout and a primary RPC on another chain do not cause a fallback. The exception is the chain ID check before a write and in `ChainProvider.health_check()`: a JSON-RPC error answer to `eth_chainId` counts as a connection failure there and moves to a fallback, whose chain ID is checked first. The connection probe of `ChainProvider.health_check()` (`web3_clientVersion`, through web3's `is_connected()`) cannot tell the two apart either, so it falls back as well. A JSON-RPC error answer to `eth_blockNumber` in `ChainProvider.get_block_number()` is raised unchanged and does not fall back; `ChainClient.health_check()` reports it as `ChainConfigurationError`. One `ChainClient` call tries each RPC at most once, across all its steps. During `chain get --follow` (`get_provenance_chain()`), a JSON-RPC error answer to a link, parent or event read is now `ChainConfigurationError` ("The RPC rejected the request: ..."), as for `get()`, and does not move to a fallback; it was `ChainConnectionError`, and the CLI printed "Cannot connect to chain". The duplicate transformation check of `transform()` also uses the fallbacks: the state read on a v2 contract, and on a v1 contract the block number read and the event scan (`eth_getLogs`); when no RPC is left, `transform()` raises `ChainConnectionError` before anything is sent, where it logged a warning and went on. Other errors in that check are still logged, and the write goes on. When no RPC is left, the error is `ChainConnectionError` as before, and log lines name each RPC only in redacted form. After a fallback, the nonce comes from the new RPC, which may not yet see transactions from the same wallet that are still waiting at the RPC used before. **Behaviour change:** `ChainProvider.health_check()` raises `ChainIdMismatchError` when the RPC in use reports another chain ID, and no longer tries the fallbacks in that case. It raised `ChainConnectionError` ("Chain ID mismatch: expected ..., got ...") and moved to a fallback (#168)
- Contract reads and `build_transaction` (`eth_estimateGas`) now go to the fallback RPC after a fallback switch. `ChainProvider` created a new Web3 object for the fallback, but `DataProvenanceContract` kept the one from start-up, so contract calls still went to the failed RPC while the nonce, signing and sending used the fallback. The switch now replaces the provider of the existing Web3 object, so `ChainProvider.web3` stays the same object and everything built on it follows the switch (#200)
- `stamps extend` now works against gateways that charge for extensions. The request goes through the same paid-request path as a stamp purchase: with `--x402` a 402 is paid, with the command's Idempotency-Key, and a payment whose outcome is not known is reported with its payer, nonce and Idempotency-Key. Before, the command sent a plain request without x402, so it got a bare 402 even with `--x402`. `GatewayClient.extend_stamp()` uses the same path (#137)
- `stamps extend` has a new `--duration-hours` option (also `--duration` / `-d`, as on `upload`), at least 24. Without it or `--amount`, the gateway adds its default of 25 hours. `--amount` is now described as what it is, PLUR per chunk (legacy), not BZZ; the gateway refuses an amount worth less than 24 hours. Giving both options, a `--amount` of 0 or less, or a `--duration-hours` below 24 is refused before anything is sent, so you are not asked to pay for a request the gateway refuses. `GatewayClient.extend_stamp()` takes a `duration_hours` argument, and `amount` is now optional (#137)
- When the gateway refuses an extension, the command shows the gateway's code and message, for example `HTTP 403 STAMP_OWNERSHIP_DENIED: Cannot extend this stamp: ...`. With `--free`, it also says that a stamp you bought can be extended only with a paid request from the same wallet (`--x402`) (#137)
- A connection failure while a transaction is sent is no longer reported as "Transaction failed". If the RPC cannot be reached, times out, or answers with something that is not JSON-RPC before `send_raw_transaction` is called (nonce lookup, gas estimate, gas price, balance check), the write raises `ChainConnectionError` and the CLI prints "Cannot connect to chain" (with `--json` in `chain protect` and `chain transform --restrict-original`, `"connection_failed"`). Nothing was sent. If the connection fails once `send_raw_transaction` has been called, while sending or while waiting for the receipt, the transaction may have been sent: the write raises the new `TransactionOutcomeUnknownError`, a subclass of `TransactionUnconfirmedError`, with the transaction hash (computed from the signed transaction when the send did not return it), the explorer link and the transport error as `reason`. The CLI prints "Outcome unknown" with the hash and explorer link (with `--json`, `{"error": "outcome_unknown", ...}`; in composite commands, under `"unconfirmed"`) and exits 1. Check the transaction before you run the command again. The CLI does not sign or send a new transaction in this case. A JSON-RPC error answer from `send_raw_transaction` now also shows the hash of the signed transaction. In `chain protect` and `chain transform --restrict-original`, when the restrict step is not verified or its outcome is unknown, the hint to restrict the original by hand now starts with "After you have checked the transaction,". A JSON-RPC error answer and a receipt timeout are reported as before (#181)
- `--gas` and `CHAIN_GAS_LIMIT` now skip gas estimation. The limit was set only after the transaction was built, and building it ran `eth_estimateGas`, so `--gas` could not get past an estimation failure. The limit is now passed when the transaction is built (the new `gas` argument of each `DataProvenanceContract.build_*_tx` method), and no `eth_estimateGas` request is sent. web3 still reads the fee fields from the RPC. Because nothing estimates the transaction first, a transaction that would revert is sent with `--gas` and costs gas: it is mined with status 0 and reported as "Transaction reverted (status=0)". Without `--gas`, a revert is still found during estimation, before anything is sent. The `--gas` help text on every chain write command now says this; on `set-storage-ref` it said only "Explicit gas limit." (#180)
- `upload-collection --redundancy` now takes an erasure coding level from 0 to 4 and sends it to the gateway as a number. It sent `redundancy=true`, which the gateway rejects with HTTP 422, so every upload with `--redundancy` failed after the stamp was bought. Without `--redundancy`, no level is sent and the gateway uses level 2, as before. **Behaviour change:** `--redundancy` without a level is now a usage error; give the level, for example `--redundancy 2`. `GatewayClient.upload_manifest()` takes `redundancy` as an integer from 0 to 4 or `None`, and raises `ValueError` for any other value, including `True` (#138)
- `upload-collection` now waits until the stamp is usable before it uploads, the same way as `upload`, and has the same `--stamp-retries` (default 12) and `--stamp-interval` (default 20 seconds) options. It uploaded right after buying the stamp, so the upload could fail on a stamp that was not usable yet, after an x402 payment for the stamp. If the stamp does not become usable, the command exits 1 without uploading and shows how to reuse the stamp (#138)
- `upload` and `upload-collection` now reject `--stamp-retries` below 1 and a negative `--stamp-interval` with a usage error (exit 2) before a stamp is bought. A negative interval ended in a traceback after the stamp was bought, and `--stamp-retries 0` failed without checking the stamp (#138)
- `upload-collection --json` now prints a JSON document when the upload succeeded and was paid but the gateway could not return the result (`IDEMPOTENCY_KEY_DELIVERED_NOT_STORED`). It printed no JSON, only an explanation on stderr, and exited 0, so a script that parsed stdout failed. The document has the usual collection metadata with `swarm_reference` set to `null`, plus `status` (`"delivered_not_stored"`), `transaction`, `payer` and `idempotency_key`. The exit code is still 0, and the explanation is still printed to stderr (#153)
- `upload-collection` now removes its temporary TAR archive on every exit, including when getting the stamp fails. It was left in the system temporary folder when the stamp purchase or pool acquisition failed (#138)
- **Behavior change:** with `--chain base` or `--chain base-sepolia` (or `CHAIN_NAME`), a custom RPC that reports a different chain ID is now a `ChainIdMismatchError` (a new subclass of `ChainConfigurationError`, with `chain`, `expected_chain_id` and `actual_chain_id`) that names both chain IDs. When the RPC answers at start-up, the command fails before anything is read or signed. The CLI prints the error with its advice to set `CHAIN_NAME=localhost` and `CHAIN_RPC_URL` for a local node, without the PROVENANCE_WALLET_KEY hint that other configuration errors get. The chain ID was taken from the node, so a `base-sepolia` configuration with a mainnet RPC would have signed mainnet transactions. If you run a local node (Hardhat, Anvil) with the default `CHAIN_NAME=base-sepolia`, set `CHAIN_NAME=localhost` and `CHAIN_RPC_URL` to the node's URL (the `--chain` option does not accept `localhost`); the `localhost` preset still takes the chain ID the node reports. The client also reads the RPC's chain ID once before its first signature, for the preset RPC too. If the custom RPC could not be reached when the client started and later answers on another chain, the write raises `ChainIdMismatchError`; if it still cannot be reached, the write raises `ChainConnectionError`. In both cases nothing is signed or sent. Reads are not checked again, so they may be served by such an RPC once it comes up. With the `localhost` preset, this check takes the chain ID the node reports (#142)
- A fallback RPC is no longer switched to when it reports a different chain ID than the one in use; it is skipped with a warning. `get_block_number` switched to a fallback without checking its chain ID (#142)
- Transactions take their nonce from the `pending` block (`eth_getTransactionCount(address, "pending")`), so a write sent while an earlier one from the same wallet is not yet mined no longer reuses its nonce (#142)
- Gateway answers with null fields no longer fail validation. The gateway can send null for `StampDetails.usable` and `immutableFlag`, `WalletResponse.bzzBalance`, `ChequebookResponse.availableBalance` and `totalBalance`, and `DataDownloadResponse.content_type`; the CLI required them, so `stamps list`, `stamps info`, `wallet` and `chequebook` failed with a pydantic validation error. These fields are now optional, and the CLI prints `unknown` (or `Unknown` for usability) instead of `None` or `None%`. With the gateway backend, `stamps info` shows `Local: Yes/No` (the batch is on this gateway's node) instead of `Exists`: the gateway sends no `exists` field, so the line always read `No`. The verbose usability check of `upload` no longer prints `Exists=` either. `StampDetails.exists` stays, always `None` from the gateway (#143)
- `stamps list` and `stamps info` show the stamp's utilization as the gateway's `utilizationPercent`. They printed `utilization` followed by `%`, but that field is the raw bucket fill level: a depth-17 batch at 50 % showed `1%`. `StampDetails` has the new optional field `utilizationPercent`; `utilization` is unchanged. When the percentage is null, the CLI prints `unknown` (#143)
- `ManifestUploadTiming` now has the gateway's fields (`stamp_validate_ms`, `file_read_ms`, `bee_upload_ms`, `total_ms`, `tar_validate_ms`, `tar_count_ms`, `file_count`, `ms_per_file`, `files_per_second`) as floats. It declared `stamp_check_ms`, `upload_ms` and `total_ms` as integers, so a fractional `total_ms` failed validation after the upload had succeeded; `upload-collection --verbose` asks for timing. `stamp_check_ms` and `upload_ms` are kept for older gateways (#143)
- An upload answer without a Swarm reference (missing, empty or whitespace only) is an error for `upload_data`, `upload_data_with_signing` and `upload_manifest`. Unpaid uploads raise `ConnectionError` ("the gateway answered HTTP 200 but sent no Swarm reference"); paid uploads raise `PaymentSettledNotDeliveredError`. Before, only paid signed and manifest uploads were checked: the others returned an empty reference and the CLI printed SUCCESS (#143)
- A success whose `X-PAYMENT-RESPONSE` receipt says `success: false` now raises `PaymentOutcomeUnknownError`, on the first attempt as on retries. On the first attempt it raised `PaymentTransactionFailedError` with "The gateway may have used free tier instead". The gateway sends the receipt only after a successful settlement and never falls back to the free tier, so that text was wrong. `PaymentTransactionFailedError` is still exported but no longer raised (#143)
- `GatewayClient.list_pool_stamps()` calls `GET /api/v1/pool/available`, the gateway's route, and reads its bare list. It called `/api/v1/pool/stamps`, which does not exist (#143)
- Notary refusals of a signed upload are shown as text. `INVALID_DOCUMENT_FORMAT` printed the gateway's whole error object as a dict, and the `ValueError` for `INVALID_SIGN_OPTION` was caught by the client itself and replaced by a generic HTTP error. The four notary codes are now read the same way as other gateway errors, so they are also recognized on older gateways that send the code only under `detail`. This covers #194 (#143)
- A 422 validation error shows each field's full message; each was cut at 60 characters. The whole message is still limited to 500 characters, and "and N more" stays at the end. This covers #193
- Gateway text in the report printed after a payment that may have been taken is cleaned of control and invisible formatting characters, so a terminal escape sequence in a gateway answer can no longer erase or hide the "do not re-run" warning. This covers the settlement transaction from the `X-Payment-Transaction` header and the `X-PAYMENT-RESPONSE` receipt, the message, label and transaction of a 202 `PURCHASE_PENDING` answer (the message is also limited to 300 characters), and the transaction and nonce of the `IDEMPOTENCY_*` answers. A transaction or nonce that is not a string is ignored, and the client's own value is kept. The `PURCHASE_PENDING` depth is kept only when it is an integer. The EIP-712 name or version advertised in a 402 `extra` is shown with escapes, for example `'USD\x1b[2KCoin'`, and limited to 64 characters in the `X402ConfigurationError` message (#151)
- `.env` is now found from the folder you run the command in: that folder first, then each parent folder up to the root, and the first `.env` found is used. It was found from the folder the package is installed in, so with the editable install from the README the repository's `.env`, with its keys and auto-pay settings, applied wherever you ran the CLI, and with a virtual environment under your home folder `~/.env` applied. **Behaviour change:** if you kept your settings in the repository's `.env` and run the CLI from other folders, copy that `.env` to the folder you work in, or export the variables. Variables already set in the environment still take precedence over `.env` (#141)
- The x402 signing key is now read the same way by the signer and by `x402 status` / `x402 balance` (`resolve_x402_private_key()`). If `X402_PRIVATE_KEY_ENV` names a variable other than `X402_PRIVATE_KEY`, only that variable is read; otherwise `X402_PRIVATE_KEY` is read, then the legacy `SWARM_X402_PRIVATE_KEY`. Before, `X402_PRIVATE_KEY_ENV` changed only the status display and the signer always read `X402_PRIVATE_KEY`; and a key in `SWARM_X402_PRIVATE_KEY` signed payments while `x402 status` showed "Not set". **Behaviour change:** with `X402_PRIVATE_KEY_ENV` set to another name, a key in `X402_PRIVATE_KEY` is no longer used. `x402 status` names the variable the key came from, never the key. Spaces and line breaks around the key are removed, and a blank value counts as not set. If `X402_PRIVATE_KEY_ENV` is not a valid variable name (letters, digits and `_`, not starting with a digit) or contains a run of 32 or more hex digits anywhere (it looks like a key), no key is read, and the signer, `x402 status` and `x402 balance` say "X402_PRIVATE_KEY_ENV is not a valid variable name" without repeating the value. A valid custom name made only of hex digits is used but not printed; messages say "the variable named by X402_PRIVATE_KEY_ENV" instead (#141)
- `X402_RPC_URL` is now used for the x402 USDC balance and EIP-712 domain checks (an explicit `rpc_url` argument to `X402Client` still comes first). It was documented but ignored. Errors that repeat it are redacted like the chain RPC URLs (#141)
- Paid requests retried with the same `Idempotency-Key` now report the authorization (nonce) that the gateway charged. If the retry gets a new success (no `Idempotent-Replayed` header), the `x402_on_payment_sent` hook gets the retry's nonce. Before, it got the earlier attempt's nonce, and that attempt timed out or was refused as already used. If the retry gets a replayed answer, the payment details on the response name the earlier attempt, because the replay answers that attempt. Before, they named the retry's nonce, which was never collected. This affects the nonce in `StampPurchasePendingError` and in the `PaymentSettledNotDeliveredError` raised when the gateway's success response cannot be read. These changes are visible to SDK callers and in payment error details. The CLI's "Payments sent" total adds amounts and counts payments, so it does not change (#156)
- `CHAIN_RPC_URLS` (comma-separated) is now passed to the chain client as the fallback RPC URLs, replacing the preset fallbacks. It was documented but ignored (#141)
- The auto-pay limit is now compared exactly, as the decimal value you set. It was compared as a binary float, so a limit that a float cannot hold exactly refused a payment of exactly that amount: with `X402_MAX_AUTO_PAY_USD=0.30`, a payment of 0.30 USDC was refused. `X402_MAX_AUTO_PAY_USD` and `--max-pay` are read as written, not rounded to a float (#152)
- An auto-pay limit that is not a finite number of 0 or more (for example `abc`, `0,30`, `nan`, `inf` or `-1`) is now a configuration error. Only plain decimal or scientific numbers in ASCII digits are accepted, so `0_30` (which Python reads as 30) and non-ASCII digits are refused too. `GatewayClient` raises `ValueError` when it is created. The CLI exits 1 with an error for an invalid `--max-pay`, and for an invalid `X402_MAX_AUTO_PAY_USD` when a command builds a client that can pay; `x402 status` and `--help` still work and `x402 status` shows a warning. A value that was not a number was replaced by 1.00 without a message, so a typo could raise the limit; NaN raised `decimal.InvalidOperation` when a payment was checked; and an infinite limit auto-paid any amount. A blank `X402_MAX_AUTO_PAY_USD` still means the default, 1.00. A very large limit is shown in scientific notation, such as `$1E+30`, and a limit with more than 6 decimals is shown with all of them (`$0.2999999`, not `$0.300000`). **Behaviour change:** `X402_MAX_AUTO_PAY_USD=inf` no longer works; use a large finite value. **Behaviour change:** a non-numeric `X402_MAX_AUTO_PAY_USD` is no longer replaced by 1.00: commands that pay exit 1 until it is fixed. A non-numeric `--max-pay` now exits 1 with this error instead of the usage error (exit 2) (#152)
- `stamps info`, `stamps extend` and `stamps check` now accept a stamp ID with a `0x` prefix and drop the prefix, as `--stamp-id` on `upload` and `upload-collection` does. A `0x`-prefixed ID made these commands fail with "Failed to ..." errors. An ID that is not 64 hex characters is refused with "STAMP_ID is not a stamp ID (64 hex characters)" before any request is sent (#159)
- Library users: `swarm_client.get_stamp_info` raises `ValueError` for a stamp ID that is not 64 hex characters (including a `0x` prefix) before it builds the URL, as `GatewayClient.get_stamp` does. Before, the ID went into the URL path unchecked (#159)
- `health` no longer reports an unhealthy backend twice. After "✗ Status: Unhealthy" it also printed a second "✗ Backend" line and "✗ Status: Unreachable". `notary verify` no longer prints an empty "ERROR: Failed to get notary address:" line after "ERROR: Gateway notary has no address configured." (#192)
- Read-only chain commands (`chain verify`, `chain get`, `chain get --follow`, `chain lookup`, and `chain status` without `--set`) no longer need a wallet key. They failed with "No wallet private key configured" when `PROVENANCE_WALLET_KEY` was not set. Commands that write to the chain, and `chain balance`, still need the key and fail as before without it. `ChainClient` has a new `require_wallet` parameter: with `require_wallet=False`, the key is read on first use, so read methods work without one, and writes, `balance()` and `address` raise `ChainConfigurationError` before anything is sent. The default, `True`, keeps the current behaviour (#140, #201)
- `redact_urls()` now redacts a URL that comes directly after a digit, an underscore or a percent-encoded character, for example `rpc_https://host/v2/<key>` or `%22https://host/v2/<key>`, and a URL that comes directly after more than 31 letters. These URLs were returned unchanged unless the chain client had registered their secret parts, so a library caller that redacts other URLs was not protected (#190)
- `ChainClient` read methods (`get`, `verify`, `get_by_storage_ref`, `balance`, `get_provenance_chain`) now raise `ChainConnectionError` for a transport failure, a timeout or an answer that is not JSON-RPC, and `ChainConfigurationError` ("The RPC rejected the request: <message>") for a JSON-RPC error answer. They let the raw `requests` or web3 exception through before, and its text repeated the full RPC URL with its API key. The messages and `rpc_url` are redacted. Other exceptions, for example a contract that cannot decode the answer, are not changed. Write methods do not change how they classify errors, except where they call `get()`, such as the check of `anchor` for an existing record. `health_check` already raised `ChainConnectionError`. **Behaviour change:** library code that catches `requests` or web3 exceptions from these methods must catch `ChainError` subclasses instead (#187)
- After an RPC failure, the `chain` commands that read print what they print for other chain errors, because the read methods now raise chain errors. `chain balance`, `get` (also with `--json` and `--follow`), `verify`, `lookup` and `status <hash>` print the redacted `  RPC URL: ...` line after `ERROR: Cannot connect to chain: ...`, as the write commands do. `chain anchor` (also with `--json` and `--owner`) prints this line too when the contract code check works but the check for an existing record fails at the RPC. `chain protect --anchor-new` reports such a failure of the new hash's check as a failed anchor step: `ERROR: Failed to anchor new hash. Cannot connect to chain: ...` (or `ERROR: Failed to anchor new hash: The RPC rejected the request: ...`), and with `--json` its JSON result has `"failed_step": "anchor"`. Before, it printed the same error without the step name, and printed no JSON. `chain protect --json` prints its JSON result, with `"failed_step": "verify"` and an `"error"` of `connection_failed` (or `chain_error` for a JSON-RPC error answer), instead of a text error. The error text is unchanged. With `-v`, these commands still print the traceback with URLs redacted before the error. The traceback now ends with the chain error, and the original `requests` or web3 error appears above it as a `RedactedException`. These commands now also print the traceback with `-v` for other chain errors they report, except "not registered". For `chain anchor` this applies to its connection errors and to chain errors other than transaction, funds and "already registered" errors, for example a failed contract code check. For the anchor step of `chain protect --anchor-new`, it applies to every error (#187)
